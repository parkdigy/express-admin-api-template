# Express Template 오케스트레이터

## 언제 사용하는가

- API, DB, 런타임 중 두 계층 이상의 계약이 함께 바뀌는 작업
- 요청 단위 트랜잭션, 서버 수명주기, 스케줄러 또는 배포 경계를 검토하는 작업
- 단일 파일의 단순 수정이나 테스트 보강에는 사용하지 않는다.

## 필요한 입력

- 목표와 관찰 가능한 완료 기준
- 변경 대상 URI·응답·인증·DB 계약과 영향받는 실행 환경
- 실제 DB 스키마 변경 방법 및 외부 서비스·배포 작업의 허용 범위

정보가 빠졌다면 인접 구현과 설정에서 가장 좁은 가정을 찾고, 실제 스키마나 외부 부작용처럼 저장소만으로 확정할 수 없는 항목은 미검증 경계로 남긴다.

## 순차 절차

1. `git status --short`로 사용자 변경을 확인하고, 요청과 인접한 route·controller·query·model·test만 읽는다.
2. 현재 계약을 URI/method, 입력 우선순위, 인증, 성공·오류 응답, DB 읽기·쓰기, 외부 부작용으로 요약한다.
3. 변경이 필요하면 모델/Knex 타입 → query → `db` 연결/export → controller → route 순서로 계약을 맞추고, 환경변수는 `.env.example`까지 동기화한다.
4. 같은 `req`가 모든 builder에 전달되는지, 필요한 `db.trans.begin(req)`이 있는지, controller 반환 전에 비동기 작업이 모두 `await`되는지 확인한다.
5. 정상·입력 오류·인증 실패·DB 실패를 검토한다. 외부 호출이 있으면 `외부 성공 → DB 실패 → 재시도`와 중복 실행 조건도 별도로 검토한다.
6. 가장 가까운 테스트를 먼저 실행한 뒤 `npm run verify`를 실행한다. 번들 계약을 바꿨고 생성물 쓰기가 허용되면 `npm run build:webpack`을 추가한다.
7. 소스 검증 결과와 실제 DB·Redis·HTTP·PM2·외부 서비스에서 확인하지 못한 영역을 나눠 보고한다.

이 흐름은 결합도가 높은 계약을 한 소유자가 순서대로 통합하는 Pipeline 방식이다. 읽기 전용 탐색이나 독립 리뷰만 병렬화할 수 있으며, 같은 파일을 여러 작업자가 동시에 수정하거나 상태를 공유하는 테스트를 병렬 실행하지 않는다.

## 참조 선택

- 라우트·인증·컨트롤러·DB 작업에만 [API와 DB 계약](references/api-db.md)을 읽는다.
- 앱 초기화·전역·스케줄러·배포 작업에만 [런타임과 운영 경계](references/runtime-ops.md)를 읽는다.
- 두 영역이 모두 관련된 경우에만 두 문서를 모두 읽는다.

## 산출물

- 구현: 동기화된 소스·테스트, 실행한 검증과 남은 라이브 확인 항목
- 분석: 원인과 근거 경로, 영향 범위, 재현·확인 조건
- 중단: 필요한 권한·스키마·외부 계약과 안전하게 진행할 수 없는 이유
